# AGENTS.md

## Project

PSU Hospital Kiosk Map is an unofficial third-party web application for helping visitors find the locations of healthcare service kiosks inside Prince of Songkla University Hospital (PSU Hospital).

This project is a kiosk **location finder/map**, not the kiosk system itself.

The actual hospital kiosks are operated by the hospital and may support healthcare entitlement workflows such as:

- Social Security
- NHSO / Universal Coverage Scheme (UCS / บัตรทอง)
- Comptroller General's Department / Civil Servant Medical Benefit Scheme (CSMBS / กรมบัญชีกลาง)
- Payment of applicable remaining/out-of-pocket amounts through PromptPay QR codes generated by the hospital kiosk system

The project does **not** implement or integrate with these systems.

---

## Core Scope

The application should help a visitor answer:

> "Where is the kiosk I need to use?"

The primary flow is:

1. Browse available kiosks.
2. Search for a kiosk or supported entitlement/service.
3. Filter by building and floor when useful.
4. Select a kiosk.
5. View its location description and supported functions.
6. Open the corresponding building/floor map.
7. Highlight the kiosk on the floor plan.

The application should remain simple, fast, accessible, and easy to maintain.

---

## Explicit Non-Goals

Do NOT implement or simulate:

- Healthcare entitlement verification
- Patient registration
- Patient information
- Hospital backend systems
- Social Security APIs
- NHSO APIs
- Comptroller General's Department APIs
- PromptPay payment processing
- QR payment generation
- Payment confirmation
- Patient medical records
- Authentication for hospital staff
- Real-time kiosk hardware status
- Indoor GPS or blue-dot positioning
- Turn-by-turn indoor navigation
- Complex admin/back-office systems
- Microservices
- Message queues
- Redis
- A database unless a concrete requirement appears later

Do not attempt to reverse engineer or connect to the hospital's internal kiosk software.

## Recommended Stack

Use:

- Next.js
- App Router
- TypeScript
- Tailwind CSS
- Zod when useful for validating structured data
- JSON files as the initial data source
- SVG floor plans where available
- Vitest for focused unit tests
- Playwright for a small number of critical end-to-end tests

Avoid adding dependencies unless they solve a real project requirement.

---

## Architecture

Prefer a small modular application with these logical areas:

- Presentation/UI
- Kiosk search/filter logic
- Domain/data definitions
- Floor-map rendering
- Optional API boundary only when there is a concrete need

Keep domain data independent from UI components.

Kiosk records should not contain UI-specific markup or duplicated presentation logic.

Do not over-engineer the application.

---

## Data Model

Use stable machine-readable IDs.

Never use display names as foreign keys.

Core entities:

- Building
- Floor
- Map
- Service
- Kiosk

A kiosk should contain enough information to locate it, for example:

- id
- nameTh
- nameEn
- buildingId
- floorId
- mapId
- position
- locationDescriptionTh
- locationDescriptionEn
- services

Additional fields may be introduced when there is a real requirement.

Do not create complex schemas merely for theoretical future use.

---
